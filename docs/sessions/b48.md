## Mục tiêu

Cuối buổi, học viên:

1. Giải thích được **luật phụ thuộc** (Dependency Rule): code bên trong không biết code bên ngoài.
2. Phân biệt 4 tầng và biết đặt 1 đoạn code mới vào đâu (bảng trong `architecture.md`).
3. Áp dụng **Dependency Inversion**: Application khai báo interface (port), Infrastructure cài đặt (adapter).
4. Refactor theo **bước nhỏ an toàn**: mỗi bước build + test xanh rồi mới đi tiếp; hành vi HTTP không đổi.
5. Chuyển migration sang project khác mà **không** làm hỏng database đang chạy.
6. Viết **architecture test** để luật kiến trúc được máy kiểm tra, không chỉ nằm trên slide.

## Mở đầu — vấn đề của `b47` (20 phút)

Mở `OrdersController.cs` ở `b47` (~235 dòng). Hỏi lớp: *"Controller này biết những gì?"* → ghi lên bảng:

- HTTP (route, policy, `CreatedAtAction`, `Problem(...)`)
- EF Core (`Include`, `ThenInclude`, `AsNoTracking`, `EF.Property<int?>(o, "UserId")`, `db.Entry(...)`)
- Domain (`Cart`, `Order.Checkout`, `PaymentFactory`)
- SignalR (`IOrderNotifier`)
- Luật IDOR (khách chỉ xem đơn của mình) — **và luật này bị chép lại trong `OrderHub.WatchOrder`**

*"Muốn đổi SQL Server sang PostgreSQL, đổi Redis sang cache khác, hoặc thêm 1 cửa vào gRPC — sửa bao nhiêu chỗ?"*

Vẽ vòng tròn đồng tâm: **Domain** ở giữa → **Application** → **Infrastructure / Api** ở ngoài. Mũi tên phụ thuộc chỉ **vào trong**.

> **Giảng viên nói:** "Clean Architecture không phải 'chia nhiều project cho đẹp'. Nó trả lời 1 câu: *khi chi tiết kỹ thuật thay đổi, nghiệp vụ có phải sửa không?* Câu trả lời đúng là: không."

Nhấn mạnh luật chơi của buổi hôm nay: **không đổi hành vi**. 137 test hiện có là hợp đồng; refactor xong mà phải sửa test (ngoài dòng `using`) nghĩa là ta đã đổi hành vi.

### Câu hỏi quan trọng: database đang chạy có hỏng không?

`__EFMigrationsHistory` chỉ lưu **Id** migration (`20261009114128_InitialCreate`...), không lưu namespace. Giữ nguyên tên file + `[Migration("...")]` → DB cũ coi như "đã cập nhật".

```bash
# Chứng minh: model sau khi chuyển KHÔNG khác snapshot → migration sinh ra rỗng
dotnet ef migrations add Probe -p src/CyberCafe.Infrastructure -s src/CyberCafe.Api -o Persistence/Migrations
# → Up() / Down() rỗng. Xóa 2 file *_Probe*.cs (giữ snapshot EF vừa sắp xếp lại).
dotnet ef database update -p src/CyberCafe.Infrastructure -s src/CyberCafe.Api
# → "No migrations were applied. The database is already up to date."
```

⚠️ **Lỗi hay gặp:** quên `-s src/CyberCafe.Api` → "Unable to create a 'DbContext'..." vì Infrastructure không có `Program.cs`/connection string. `-p` = project chứa migration, `-s` = project khởi động (đọc cấu hình).

⚠️ **Lỗi hay gặp:** đổi **tên class** migration hoặc sinh lại migration từ đầu "cho sạch" → DB của đồng đội có lịch sử khác → `There is already an object named 'Products'`.

Test: `ReportsAndModelTests.Migrations_AreUpToDate` vẫn xanh.

## Bước 3 — Identity: cả khối sang Infrastructure, sau `IAuthService` (10 phút)

`User.cs` (b47) đã ghi sẵn: *"Buổi 48 sẽ chuyển phần này vào Infrastructure"*. Chuyển `User`, `RefreshToken`, `JwtOptions`, `TokenService`, `BCryptPasswordHasher`, `AuthService`, `DevAccountSeeder` → `Infrastructure/Identity`.

- Application chỉ giữ hợp đồng: `IAuthService` (vào `LoginRequest`, ra `AuthResponse`).
- `AuthService` **vẫn dùng `DbContext` trực tiếp** — nó đã ở tầng hạ tầng. *"Repository là để Application không phải biết EF; code đã nằm trong Infrastructure thì không cần giấu EF khỏi chính nó"* (ADR 0002 mục 4).
- `IPasswordHasher`, `ITokenService` ở lại Infrastructure: chỉ code Infrastructure gọi. **Port chỉ đặt ở Application khi Application cần gọi.**
- `JwtBearer` (kiểm token ở mỗi request) **ở lại Api**: nó là middleware của cửa vào HTTP.

## Bước 4 — Exception nghiệp vụ thay cho `NotFound()` / `Problem(...)` (10 phút)

Use case không được trả `IActionResult` (đó là ASP.NET Core). Thay vào đó ném exception **có nghĩa**:

| `b47` trong controller | `b48` trong use case | HTTP (handler) |
|------------------------|----------------------|----------------|
| `ModelState.AddModelError(...)` + `ValidationProblem(...)` | `throw ValidationException.For("Items", "...")` | 400 |
| `return NotFound()` | `throw new NotFoundException(...)` | 404 |
| `Problem(409, "Không xóa được món", ...)` | `throw new ConflictException(detail, "Không xóa được món")` | 409 |

`DomainExceptionHandler` thêm 3 dòng `switch`; `HttpValidationProblemDetails` cho ra **cùng hình dạng** `{ "errors": { "Items": [...] } }` → Web (`ApiClientBase`) không phải sửa.

Câu hỏi cho lớp: *"Truy vấn không thấy (GET /api/orders/42) có nên ném exception không?"* → Ở đây: **truy vấn** trả `null` (controller → `NotFound()`), **lệnh** (sửa/xóa/đổi trạng thái) ném `NotFoundException`. Không có đáp án tuyệt đối — quan trọng là nhất quán.

## Bước 6 — Port truy cập dữ liệu + repository hẹp (20 phút)

Mở lại ADR 0001: *"Khi Application không được tham chiếu EF Core mới thật sự cần interface truy cập dữ liệu"* — chính là bây giờ.

Viết interface theo **nhu cầu của use case**, không phải `IRepository<T>` chung chung:

```csharp
public interface IProductRepository
{
    Task<PagedResult<ProductDto>> GetPageAsync(ProductQuery query, CancellationToken ct = default); // đọc: DTO projection
    Task<Product?> FindAsync(int id, CancellationToken ct = default);                                // ghi: entity tracked
    Task<IReadOnlyDictionary<int, Product>> GetByIdsAsync(IReadOnlyCollection<int> ids, ...);
    Task<bool> IsSoldAsync(int productId, ...);
    void Add(Product product); void Remove(Product product);
}
```

`ProductRepository` (Infrastructure): **cắt-dán nguyên** LINQ từ `ProductsController` b47. `OrderRepository`: `Include/ThenInclude`, shadow property `UserId` (`db.Entry(order).Property(...)`, `EF.Property<int?>(...)`).

Thảo luận 3 phương án (bảng trong ADR 0002): `ICyberCafeDbContext` có `DbSet<T>` / `IRepository<T>` / port hẹp. Cho lớp tự tìm lý do A vi phạm luật của buổi (Application phải cài gói EF Core).

⚠️ **Lỗi hay gặp:** `IProductRepository.Query()` trả `IQueryable<Product>` → Application viết `.Include(...).ToListAsync()` → lại cần EF Core. Port phải trả **kết quả**, không trả "câu truy vấn chưa chạy".

⚠️ **Lỗi hay gặp:** `services.AddScoped<IUnitOfWork, CyberCafeDbContext>()` → DI tạo **DbContext thứ hai**; repository `Add` vào DbContext A, `SaveChanges` gọi trên DbContext B → không lưu gì, không báo lỗi. Đúng: `AddScoped<IUnitOfWork>(sp => sp.GetRequiredService<CyberCafeDbContext>())`.

## Bước 9 — Adapter SignalR generic theo hub (10 phút)

Bài toán: `SignalROrderNotifier` cần `IHubContext<OrderHub, IOrderClient>`. `OrderHub` là **cửa vào** (như controller) → ở Api. Nhưng Infrastructure **không được** tham chiếu Api.

Gỡ bằng generic:

```csharp
public class SignalROrderNotifier<THub>(IHubContext<THub, IOrderClient> hub, ...) : IOrderNotifier
    where THub : Hub<IOrderClient>

// Program.cs (Api — composition root, nơi DUY NHẤT biết cả 2 phía)
builder.Services.AddOrderNotifier<OrderHub>();
```

`IOrderClient` chuyển sang `Infrastructure/Realtime` (adapter cần nó; Api vẫn thấy vì Api tham chiếu Infrastructure).

## Exit ticket

1. Phát biểu luật phụ thuộc (Dependency Rule) trong 1 câu.
2. Vì sao `ICyberCafeDbContext` có `DbSet<T>` đặt ở Application **không** hợp với CyberCafe?
3. `AuthService` vẫn dùng `DbContext` trực tiếp — có vi phạm Clean Architecture không? Vì sao?
4. Chuyển migration sang project khác: điều gì phải giữ nguyên để DB cũ không hỏng?
5. Vì sao `SignalROrderNotifier` là class generic `<THub>`?
6. 137 test cũ vẫn xanh chứng minh điều gì? Không chứng minh điều gì?

**Đáp án gợi ý:** (1) Code ở vòng trong không được biết (tham chiếu, gọi, đặt tên) bất cứ thứ gì ở vòng ngoài. (2) `DbSet<T>` là kiểu của EF Core → Application phải cài gói EF → vi phạm chính luật đang dạy; ngoài ra LINQ/Include lại rải trong use case. (3) Không: `AuthService` nằm ở Infrastructure, cùng tầng với EF Core; luật chỉ cấm tầng **trong** biết tầng ngoài. (4) Id migration (tên + `[Migration("...")]`) và model (snapshot) — `__EFMigrationsHistory` so theo Id. (5) Cần kiểu hub cho `IHubContext<THub,...>`, mà hub ở Api; Infrastructure không được tham chiếu Api → để Api (composition root) truyền kiểu vào. (6) Hành vi quan sát được qua HTTP/SignalR không đổi; **không** chứng minh kiến trúc đúng — vì vậy cần thêm architecture test.
