## Mục tiêu

1. Phân biệt **entity**, **value object**, **aggregate**, **aggregate root** (lý thuyết đủ dùng, không sa vào thuật ngữ).
2. Nhận ra "anemic domain model" (class chỉ có property, luật nằm ở service) trong code `b48`.
3. Biến `Order` thành aggregate root: **không setter public**, thay đổi qua method có tên nghiệp vụ, tự giữ **invariant**.
4. Map aggregate bằng EF Core mà **không đổi lược đồ** database.
5. Viết unit test cho invariant — không cần database.

## Mở đầu — "ai đang giữ luật?" (15 phút)

Mở `b48`: `Domain/Orders/Order.cs`, `Application/Orders/OrderService.cs`. Cho lớp tìm lỗ hổng:

```csharp
Order order = cart.ToOrder(customer);
order.Checkout(new CashPayment(0, 50000));
order.Checkout(new CashPayment(0, 50000)); // trả tiền 2 lần — không ai chặn
order.Items[0].Quantity = 99;              // sửa số ly SAU KHI đã thu tiền — tổng tiền lệch số đã thu
order.ChangeStatus(OrderStatus.Preparing); // pha đơn chưa trả tiền? (luồng Cart.ToOrder không bắt buộc Checkout)
```

Luật "khách chỉ hủy khi Pending" lại nằm trong `OrderService` — gọi `order.ChangeStatus(Cancelled)` từ chỗ khác là lách được.

> **Giảng viên nói:** "Domain 'thiếu máu' (anemic): class chỉ là túi dữ liệu, luật nằm rải ở service. Ai quên gọi service là phá luật. DDD nói: luật của đơn hàng phải nằm TRONG đơn hàng — ai cầm `Order` cũng không làm sai được."

Vẽ lên bảng aggregate `Order`:

```
┌──────────── Aggregate "Order" ────────────┐
│  Order (ROOT)  ── OwnerId (Id tài khoản)   │  ← bên ngoài chỉ được giữ tham chiếu tới ROOT
│   ├─ OrderItem × n  ── Product (tham chiếu)│
│   ├─ Discount?                             │
│   ├─ Payment?                              │
│   └─ Customer (ảnh chụp tên/SĐT/điểm)      │
└────────────────────────────────────────────┘
```

Luật của aggregate: (1) chỉ đổi qua root; (2) lưu/tải **cả cụm** trong 1 transaction; (3) tham chiếu aggregate khác **bằng Id** (Order → `OwnerId`, không giữ object `User`).

## Bước 1 — `AggregateRoot` + `DomainException` (15 phút)

- `Domain/Common/AggregateRoot.cs`: lớp cha giữ `DomainEvents` (buổi 50 dùng), `Raise(...)` là `protected`.
- `Domain/Common/DomainException.cs`: `DomainException : InvalidOperationException` — "dữ liệu đúng nhưng **lúc này** không được làm".
- `Api/Errors/DomainExceptionHandler.cs`: thêm nhánh `DomainException => 409` **trước** nhánh `InvalidOperationException` (switch chọn nhánh khớp đầu tiên).

⚠️ **Lỗi hay gặp:** ném `DomainException` cho SĐT sai định dạng. Sai **định dạng** → `ArgumentException` (400). Đúng định dạng nhưng **vi phạm trạng thái** → `DomainException` (409).

## Bước 2 — Factory method + `AddItem` / `ApplyDiscount` (25 phút)

```csharp
public static Order Create(Customer customer, string? note = null, int? ownerId = null) => new() { ... };
public OrderItem AddItem(Product product, DrinkSize size = DrinkSize.S, int quantity = 1) { EnsureEditable(); ... }
public void ApplyDiscount(Discount discount) { EnsureEditable(); ... }
```

- Bỏ constructor public nhận sẵn danh sách món → chỉ còn 1 cửa tạo đơn hợp lệ ban đầu.
- `AddItem` gộp dòng cùng món + size (giống `Cart`), từ chối món tạm hết (`DomainException` "… đang tạm hết" → test 409 cũ vẫn xanh).
- `EnsureEditable()` = **invariant 1**: đã thanh toán / không còn `Pending` thì không sửa.
- `OrderItem`: constructor, `Quantity` setter, `IncreaseQuantity` thành **`internal`** — chỉ `Order`/`Cart` (cùng assembly Domain) gọi được.

Hỏi lớp: *"Web có bị ảnh hưởng không khi `Quantity` không còn set public?"* → Không: Web đổi số lượng qua `CartState → Cart.UpdateQuantity` (trong Domain).

## Bước 3 — `Pay` + vòng đời bằng method có tên nghiệp vụ (25 phút)

| Trước (`b48`) | Sau (`b49`) | Invariant |
|---------------|-------------|-----------|
| `Checkout(payment)` | `Pay(payment)` | đơn rỗng / đã trả → `DomainException` |
| `ChangeStatus(Preparing)` | `StartPreparing()` | **chưa trả tiền thì chưa pha** |
| `ChangeStatus(Ready)` | `MarkReady()` | theo `OrderStatusFlow` |
| `ChangeStatus(Completed)` | `Complete()` | theo `OrderStatusFlow` |
| `ChangeStatus(Cancelled)` + if trong service | `Cancel(requestedByCustomer)` | khách chỉ hủy khi `Pending` |

`ChangeStatus(target)` vẫn giữ — nhưng chỉ để **dịch** nút barista ("Bắt đầu pha" gửi `Preparing`) sang đúng method, để luật riêng của từng bước luôn chạy. `OrderStatusFlow` giữ nguyên vì Web dùng để vẽ nút.

> **Câu hỏi:** "Tên method nào dễ hiểu với người quản lý quán hơn: `ChangeStatus(1)` hay `StartPreparing()`?" — DDD gọi đây là **ngôn ngữ chung (ubiquitous language)**.

## Bước 4 — Chủ đơn thành `OwnerId`, map EF không đổi lược đồ (20 phút)

- `b42–48`: chủ đơn là shadow property `"UserId"` — Domain không biết. DDD: "đơn của ai" là thông tin nghiệp vụ → `Order.OwnerId`.
- `OrderConfiguration`: `Property(o => o.OwnerId).HasColumnName("UserId")` + `HasForeignKey(o => o.OwnerId)` → tên cột, FK, index **giữ nguyên**.
- `builder.Ignore(o => o.DomainEvents)` và `Ignore(o => o.Code)`.
- `IOrderRepository` thu gọn còn `GetAsync(id)` (tải **nguyên cụm**, tracked) + `Add(order)` — "1 repository cho 1 aggregate root". Danh sách/chi tiết để **hiển thị** sẽ sang phía đọc (buổi 51, 53).

```bash
dotnet ef migrations add Probe -p src/CyberCafe.Infrastructure -s src/CyberCafe.Api -o Persistence/Migrations
# Up() / Down() rỗng → lược đồ không đổi. Xóa 2 file *_Probe*.cs, giữ snapshot đã làm mới.
```

⚠️ **Lỗi hay gặp:** quên `Ignore(o => o.DomainEvents)` → "The property 'Order.DomainEvents' could not be mapped…" khi dựng model.
⚠️ **Lỗi hay gặp:** tải aggregate thiếu `Include(o => o.Payment)` → `IsPaid` sai → `StartPreparing` chặn nhầm đơn đã trả tiền.

## Bước 5 — `Cart.ToOrder` đi qua aggregate (10 phút)

`Cart` là "bản nháp" phía giao diện, **không phải** aggregate. `ToOrder` giờ gọi `Order.Create` + `AddItem` từng dòng + `ApplyDiscount` → mọi invariant vẫn chạy. Handler đặt hàng (buổi 51) dựng `Order` trực tiếp, không cần `Cart`.

## Exit ticket

1. Aggregate root khác entity thường ở điểm nào?
2. Invariant là gì? Cho 2 ví dụ trong `Order`.
3. Vì sao `OrderItem.Quantity` là `internal set` mà không phải `private set`?
4. Vì sao đổi shadow property `UserId` thành `OwnerId` mà không cần migration?

**Đáp án gợi ý:** (1) Root là cửa duy nhất để đổi cả cụm, chịu trách nhiệm giữ luật cho cả cụm; bên ngoài chỉ giữ tham chiếu tới root. (2) Đã thanh toán thì không sửa món; chưa thanh toán thì không pha. (3) `Cart` và `Order` (cùng assembly Domain) cần đổi số lượng; bên ngoài Domain thì không. (4) `HasColumnName("UserId")` giữ nguyên cột/FK/index — EF so sánh lược đồ, không so tên property.
