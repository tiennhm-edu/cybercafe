await unitOfWork.SaveChangesAsync(ct);   // đơn đã lưu

Đảo thứ tự cũng không cứu: publish trước, lưu lỗi → Payment thu tiền đơn không tồn tại. SQL Server và RabbitMQ không có transaction chung → **dual write**.

## Bước 1 — Integration event (15 phút)

Project mới `CyberCafe.IntegrationEvents` (chỉ BCL):

```csharp
public sealed record OrderPlacedIntegrationEvent(Guid EventId, DateTime OccurredAtUtc, int OrderId, string OrderCode,
    decimal Amount, string PaymentMethod, string? CardLast4) : IIntegrationEvent;
```

| | Domain event (b50) | Integration event (b55) |
|-|--------------------|-------------------------|
| Phạm vi | 1 service, 1 tiến trình | Giữa service, qua broker |
| Nội dung | Tham chiếu `Order` | Kiểu nguyên thủy, JSON |
| Độ tin cậy | Best-effort sau commit | Outbox → at-least-once |
| Đổi | Tự do | Hợp đồng: chỉ thêm field |

⚠️ **Lỗi hay gặp:** gửi số thẻ đầy đủ trong message → nằm trong queue, log, file dump. Chỉ `CardLast4`.
⚠️ **Lỗi hay gặp:** dùng `enum PaymentMethod` của Domain trong event → Payment phải tham chiếu Domain của Order.

## Bước 2 — Outbox: lưu đơn + message trong 1 transaction (30 phút)

1. Port `IIntegrationEventOutbox.Enqueue(...)` (Application) ← `EfIntegrationEventOutbox` (Infrastructure): chỉ `db.OutboxMessages.Add(...)`.
2. Bảng `OutboxMessages` cùng database với `Orders`:

   ```bash
   dotnet ef migrations add AddOutboxAndInbox -p src/CyberCafe.Infrastructure -s src/CyberCafe.Api -o Persistence/Migrations
   ```

3. `OrderingSettings.PaymentFlow`: `InProcess` (b53, mặc định, test cũ) / `Messaging` (AppHost đặt `Payments__Flow=Messaging`).
4. `PlaceOrderCommandHandler`, nhánh Messaging:

   ```csharp
   orders.Add(order);
   await unitOfWork.SaveChangesAsync(ct);   // lần 1: có Order.Id (IDENTITY)
   outbox.Enqueue(new OrderPlacedIntegrationEvent(Guid.NewGuid(), DateTime.UtcNow, order.Id, ...));
   await unitOfWork.SaveChangesAsync(ct);   // lần 2: dòng outbox
   // TransactionBehavior (b52) bọc CẢ HAI → cùng commit / cùng rollback
   ```

   Đơn trả về ở trạng thái **Pending, chưa thanh toán** (`Order.IsAwaitingPayment`).
5. `OutboxMessage.TraceParent = Activity.Current?.Id` — để nối trace (Bước 7).

Test: `MessagingFlowTests.PlaceOrder_Messaging_WritesOrderAndOutboxInSameTransaction` (2 lần lưu đều trong 1 transaction đã commit, `Enqueue` trong transaction, chỉ 4 số cuối thẻ) và `..._OutboxSaveFails_RollsBackWholeTransaction`.

⚠️ **Lỗi hay gặp:** tạo DbContext riêng cho outbox → khác transaction → lại dual write.
⚠️ **Lỗi hay gặp:** EF InMemory **không có transaction** — test atomic bằng fake `TransactionalUnitOfWork`; SQL thật kiểm khi chạy AppHost.

## Bước 3 — Dispatcher + RabbitMQ (20 phút)

- `OutboxDispatcher.DispatchPendingAsync()`: dòng chưa gửi, cũ trước → `bus.PublishAsync` (MessageId = EventId) → `ProcessedAtUtc` → **lưu sau mỗi message**. Lỗi → `Attempts++`, `LastError`, lượt sau thử lại.
- `OutboxPublisherWorker : BackgroundService` + `PeriodicTimer` (`Outbox:PollingIntervalMs`); mỗi lượt 1 scope mới (DbContext là Scoped).
- MassTransit **8.5.11** (Apache-2.0 — **không** 9.x, ADR 0004): `AddOrderMessaging()` trong Infrastructure; `UsingRabbitMq` khi có `ConnectionStrings:messaging`, `UsingInMemory` khi không (test).
- AppHost: `builder.AddRabbitMQ("messaging").WithManagementPlugin()`; mở Management UI từ dashboard → xem exchange `CyberCafe.IntegrationEvents:OrderPlacedIntegrationEvent`, queue `payment-order-placed`, `ordering-payment-completed`.

Vì sao "publish rồi mới đánh dấu"? Đảo lại mà sập ở giữa = dòng "đã gửi" nhưng broker chưa nhận → mất. Giữ thứ tự này thì sập ở giữa = **gửi lại** → bên nhận phải idempotent (Bước 5). Outbox = **at-least-once**, không phải exactly-once.

Test `OutboxDispatcherTests`: round-trip JSON + traceparent, gửi theo thứ tự + đánh dấu, broker sập giữ message, span nối trace.

## Bước 4 — Payment xử lý, Order cập nhật aggregate (20 phút)

- Payment: `OrderPlacedConsumer` → `PaymentRules.Decide(...)` (vượt `Payment:MaxAmount` = 500.000 đ → từ chối; thẻ đuôi `0000` → ngân hàng từ chối) → lưu → publish `PaymentCompleted` / `PaymentFailed`. `Payment:SimulatedDelayMs` = 1500 ở Development để thấy trạng thái chờ.
- Order: consumer mỏng ở `Infrastructure/Messaging/PaymentResultConsumers.cs` → `ConfirmOrderPaymentCommand` / `RejectOrderPaymentCommand` (Application) → `order.Pay(...)` (y hệt b53, phát `OrderPaid` + `OrderPlaced` → SignalR barista **và** khách) hoặc `order.RejectPayment(reason)` (mới: → `Cancelled`, phát `OrderStatusChanged` → handler b50 có sẵn báo khách).
- Bảng quầy (`OrderReadStore.GetByStatusAsync`) chỉ lấy đơn **đã trả tiền**.
- Handler không tin mù quáng: số tiền khác `FinalAmount` → hủy; đơn không còn chờ (khách tự hủy) → `Ignored` + log "cần hoàn tiền".

Test: `PaymentRulesTests`, `OrderPaymentFlowTests` (Domain), `MessagingFlowTests.RejectPayment_...`, `PaymentMessagingTests` (Api thật + bus in-memory).

## Bước 5 — Idempotent consumer (20 phút)

| Service | Chống trùng bằng | Khi trùng |
|---------|------------------|-----------|
| Order | `IInbox` — bảng `ProcessedMessages` (khóa ghép MessageId + Consumer), lưu **cùng SaveChanges** với aggregate | Trả `Duplicate`, không làm gì |
| Payment | `ProcessedMessages` **và** `UNIQUE(OrderId)` trên `Payments` | **Gửi lại kết quả cũ** với `ResultEventId` đã lưu |

- Vì sao Payment gửi lại thay vì im lặng? Lần trước có thể sập giữa "lưu" và "publish" → nếu im lặng, đơn chờ mãi. Gửi lại cùng EventId → Order (idempotent) bỏ qua nếu đã nhận.
- 2 bản trùng chạy song song: cả 2 qua bước kiểm tra → bản sau vi phạm khóa → exception → retry → thấy "đã xử lý". **Database là trọng tài.**
- Chống trùng theo `EventId` trong message, không theo MessageId của broker → đổi broker / gửi lại từ outbox vẫn đúng.

Test: `ConfirmPayment_AppliesOnce_DuplicateIsIgnored` (không cộng điểm 2 lần), `DuplicateMessage_ChargesOnce_AndReplaysSameResult`, `SameOrderDifferentEventId_StillOneTransaction`, `PaymentCompleted_PaysOrderOnce_EvenIfDeliveredTwice`.

⚠️ **Lỗi hay gặp:** consumer ném exception cho lỗi "nghiệp vụ không áp dụng được" → MassTransit retry mãi 1 message không bao giờ thành công. Đánh dấu đã xử lý + log.

## Bước 6 — Resilience (10 phút)

| Tầng | Cấu hình | Ở đâu |
|------|----------|-------|
| HTTP (Web → Gateway, mọi HttpClient) | `AddStandardResilienceHandler`: retry (5xx/408/429/timeout), circuit breaker, timeout từng lần + tổng | `ServiceDefaults/Extensions.cs` |
| Message | `UseMessageRetry` 200 ms → 1 s → 5 s; bỏ qua `DomainException`/`ValidationException`; hết lượt → queue `_error` | `Infrastructure/DependencyInjection.cs`, `Payment.Api/Program.cs` |
| Outbox | Broker tắt → giữ dòng, thử lại mỗi giây (tối đa 10 lần) | `OutboxDispatcher` |

⚠️ **Lỗi hay gặp:** retry cả `POST /api/orders` → lần 1 thật ra đã lưu, chỉ mất response → khách có 2 đơn. `options.Retry.DisableForUnsafeHttpMethods()`.

Demo: dừng resource `payment` trên dashboard → đặt đơn (vẫn 201, "Đang xử lý thanh toán") → bật lại → message trong queue được xử lý, trang khách tự đổi.

## Bước 7 — Trace xuyên service (10 phút)

Dashboard → **Traces** → chọn `POST /api/{**catch-all}`: 1 trace gồm

```
gateway  POST /api/{**catch-all} → POST (HttpClient)
api        POST api/orders
api        outbox publish OrderPlacedIntegrationEvent      ← span tự tạo, cha = traceparent lưu trong outbox
api          CyberCafe.IntegrationEvents:OrderPlacedIntegrationEvent send   (MassTransit)
payment        payment-order-placed receive → process → PaymentCompletedIntegrationEvent send
api              ordering-payment-completed receive → process
```

Không có `TraceParent` trong outbox thì phần sau `api POST` thành 1 trace **riêng** (worker chạy nền, không có Activity) — so sánh để thấy giá trị của 1 cột.

## Bài tập

1. **Hoàn tiền (compensation):** khách hủy khi đang chờ mà Payment đã thu → Order phát `RefundRequestedIntegrationEvent` (qua outbox), Payment ghi giao dịch hoàn tiền. Có cần idempotent không?
2. **Dọn outbox/inbox:** `BackgroundService` xóa dòng `ProcessedAtUtc` cũ hơn 7 ngày. Vì sao không xóa ngay sau khi gửi?
3. **Nhiều instance Api:** 2 Api cùng quét outbox → gửi trùng. Thêm khóa dòng (`UPDLOCK, READPAST` bằng `FromSql`) hoặc chuyển sang MassTransit EF Outbox; so sánh.
4. **Gom inbox thành pipeline behavior:** `IdempotencyBehavior<TRequest,TResponse>` cho mọi command có `EventId` (giống ValidationBehavior b52) thay vì kiểm tra trong từng handler.
5. **Kafka (đọc thêm):** vẽ lại luồng nếu dùng Kafka; cái gì thay đổi về thứ tự, phát lại, consumer group?

## Exit ticket

1. Dual write là gì? Outbox chữa thế nào?
2. Vì sao Outbox cho at-least-once chứ không exactly-once?
3. Idempotent consumer của Order và của Payment khác nhau ở đâu? Vì sao Payment gửi lại kết quả cũ?
4. Vì sao không retry `POST` trong `AddStandardResilienceHandler`?
5. Cột `TraceParent` trong outbox để làm gì?

**Đáp án gợi ý:** (1) Ghi 2 hệ thống không có transaction chung; ghi message vào bảng cùng transaction với dữ liệu, worker gửi sau. (2) Sập giữa "publish" và "đánh dấu đã gửi" → gửi lại. (3) Order: trùng thì bỏ qua; Payment: trùng thì gửi lại kết quả (cùng EventId) vì lần trước có thể chưa kịp gửi; Payment còn có khóa nghiệp vụ UNIQUE(OrderId). (4) POST không idempotent — lần trước có thể đã thành công. (5) Nối span "outbox publish" (chạy nền) vào trace của request đặt hàng.
