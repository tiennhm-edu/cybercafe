## Mục tiêu

1. Giải thích **khi nào** nên (và không nên) tách microservice; vì sao chỉ tách **Payment** trước.
2. Dựng **.NET Aspire AppHost**: khai báo SQL Server, Redis, RabbitMQ + các project; `WithReference`, `WaitFor`, parameter.
3. Dùng **ServiceDefaults**: OpenTelemetry, health check, service discovery, resilience — 1 dòng cho mọi service.
4. Tạo **Payment service** (minimal API, **database riêng**, migration riêng).
5. Dựng **API Gateway bằng YARP**: route theo đường dẫn, service discovery, **JWT kiểm ở gateway** cho `/payments/*`.
6. Web chỉ gọi gateway; kiểm ranh giới service bằng architecture test.

## Mở đầu — monolith có gì sai? (15 phút)

CyberCafe ở `b53` là **modular monolith** tốt: Clean Architecture, aggregate, CQRS. Câu hỏi không phải "monolith xấu", mà "phần nào cần **deploy, mở rộng, hỏng** độc lập?".

| Lý do tách | Payment | Menu | Identity |
|------------|---------|------|----------|
| Nhóm/đối tác khác quản lý (cổng thanh toán, đối soát) | ✅ | | |
| Lỗi không được kéo sập đặt hàng (Payment chậm ≠ không đặt được) | ✅ | | |
| Dữ liệu nhạy cảm, quy định riêng (PCI) | ✅ | | ✅ |
| Tải khác hẳn phần còn lại | | ✅ (đọc nhiều — đã có cache) | |

→ Tách **Payment** trước (lợi ích rõ nhất); Menu/Identity để bài tập. Microservice là **đánh đổi**: thêm mạng, thêm broker, thêm database, nhất quán cuối cùng (eventual consistency).

> **Giảng viên nói:** "Tách service là tách **ranh giới dữ liệu** chứ không phải tách thư mục. Hai service dùng chung 1 database là 1 monolith phân tán — có đủ cái khó, không có cái lợi."

## Bước 1 — AppHost: cả hệ thống trong 1 file C# (25 phút)

```bash
# Aspire 13: AppHost là gói NuGet SDK, KHÔNG cần "dotnet workload install aspire"
# Tạo bằng tay (hoặc: dotnet new install Aspire.ProjectTemplates; dotnet new aspire-apphost)
```

`src/CyberCafe.AppHost/CyberCafe.AppHost.csproj`: `<Project Sdk="Aspire.AppHost.Sdk/13.6.1">` + `Aspire.Hosting.SqlServer/Redis/RabbitMQ` + `ProjectReference` tới 4 service.

`AppHost.cs` (đọc từ trên xuống cùng lớp):

```csharp
var sqlPassword = builder.AddParameter("sql-password", secret: true);   // giá trị: appsettings.json → Parameters
var sql = builder.AddSqlServer("sql", sqlPassword, port: 14330).WithImageTag("2022-latest").WithDataVolume("cybercafe-b55-sql");
var cafeDb = sql.AddDatabase("CyberCafe", databaseName: "CyberCafeDb");          // ConnectionStrings__CyberCafe
var paymentDb = sql.AddDatabase("PaymentDb", databaseName: "CyberCafePayments");
var api = builder.AddProject<Projects.CyberCafe_Api>("api", launchProfileName: "http")
    .WithReference(cafeDb).WaitFor(cafeDb) ...
```

- **Parameter**: bí mật/thay đổi theo máy. Giá trị **giả** trong `appsettings.json`; máy thật: `dotnet user-secrets set "Parameters:jwt-key" "..." --project src/CyberCafe.AppHost`.
- **`WithReference(x)`** = bơm biến môi trường `ConnectionStrings__x` (DB/Redis/RabbitMQ) hoặc `services__x__http__0` (project).
- **`WaitFor(x)`** = chờ `x` healthy → hết lỗi "Api chạy trước khi SQL nhận kết nối".
- Tên resource `"CyberCafe"`, `"Redis"` trùng tên connection string Api đang đọc từ b40/b47 → **Api không sửa dòng đọc cấu hình nào**.

⚠️ **Lỗi hay gặp:** đổi `sql-password` sau khi volume `cybercafe-b55-sql` đã tạo → SQL Server giữ mật khẩu cũ → Api báo `Login failed for user 'sa'`. Gỡ: `docker volume rm cybercafe-b55-sql`.
⚠️ **Lỗi hay gặp:** viết `dotnet run --project ...` bên trong comment XML của `.csproj` → MSB4025 (comment XML không được chứa `--`).

So sánh với `docker-compose.yml` (b40–b53, vẫn giữ cho các tag cũ):

| docker-compose | Aspire AppHost |
|----------------|----------------|
| Chỉ container; project chạy tay ở 2–4 terminal | Container **và** project, 1 lệnh |
| Connection string chép tay vào `appsettings.Development.json` | Tự bơm qua biến môi trường |
| `depends_on` + healthcheck tự viết | `WaitFor` dùng health check có sẵn của từng integration |
| Log mỗi nơi 1 cửa sổ | Dashboard: log, trace, metric của mọi service |

## Bước 5 — API Gateway bằng YARP (25 phút)

```bash
dotnet new web -o src/CyberCafe.Gateway
# Yarp.ReverseProxy (MIT) + Microsoft.Extensions.ServiceDiscovery.Yarp
```

```csharp
builder.Services.AddReverseProxy()
    .LoadFromConfig(builder.Configuration.GetSection("ReverseProxy"))
    .AddServiceDiscoveryDestinationResolver();     // "http://api" → service discovery
app.MapReverseProxy();
```

Bảng route nằm trong `appsettings.json` (có chú thích):

| Route | Match | Cluster | AuthorizationPolicy |
|-------|-------|---------|---------------------|
| `api` | `/api/{**catch-all}` | `api` → `http://api` | — (Api tự kiểm) |
| `hubs` | `/hubs/{**catch-all}` | `api` | — (WebSocket SignalR đi xuyên YARP) |
| `payments` | `/payments/{**catch-all}` | `payment` → `http://payment` | `AdminOnly` |

Api đứng **sau** gateway → `app.UseForwardedHeaders()` (đầu pipeline) để rate limiter đăng nhập (b47) dùng IP thật trong `X-Forwarded-For`.
⚠️ **Lỗi hay gặp:** `KnownProxies.Clear()` "cho chạy được" → ai cũng giả IP bằng cách tự gửi header. Mặc định chỉ tin `localhost` (gateway chạy cùng máy dưới AppHost).
⚠️ **Lỗi hay gặp:** `"/api/{*catch-all}"` hoặc thiếu `**` → chỉ khớp 1 đoạn; `/api/products/1` → 404 ở gateway.

## Bước 6 — JWT: kiểm ở gateway hay ở service? (15 phút)

| Cách | Ưu | Nhược | CyberCafe dùng cho |
|------|----|-------|--------------------|
| **Chỉ gateway** kiểm, service tin gateway | Service gọn, 1 chỗ cấu hình khóa | Service lộ ra mạng là mất bảo vệ; policy chi tiết (IDOR, theo endpoint) không làm được ở gateway | `/payments/*` (Payment service không mở cổng ra ngoài — chỉ `gateway`, `web` có `WithExternalHttpEndpoints`) |
| **Chuyển tiếp** token, service tự kiểm | Defense in depth; policy chi tiết đúng chỗ | Mỗi service cấu hình JWT | `/api/*`, `/hubs/*` (nhiều endpoint ẩn danh + policy `ManageMenu`, `PlaceOrders`, IDOR) |
| Cả hai | An toàn nhất | Cấu hình 2 nơi | Khuyến nghị cho môi trường thật |

Gateway dùng **cùng** Issuer/Audience/Key với Api (AppHost truyền chung parameter `jwt-key`). YARP luôn chuyển nguyên header `Authorization`.

Test (`tests/CyberCafe.Gateway.Tests/GatewayRoutingTests.cs`) — thay `IForwarderHttpClientFactory` bằng handler giả ghi lại request:

| Test | Kiểm |
|------|------|
| `Config_LoadsRoutesAndClusters` | 3 route, 2 cluster, policy `AdminOnly` |
| `ApiAndHubRoutes_ForwardToApiService` | `/api/products?page=2` → `http://api/api/products?page=2`, có `X-Forwarded-*` |
| `PaymentsRoute_IsGuardedByJwtAtGateway` | ẩn danh 401, Customer 403 (không chuyển tiếp), Admin → `payment` kèm `Authorization` |
| `UnknownPath_Is404_AndForgedToken_Is401` | route lạ 404; token sửa chữ ký 401 |

## Bước 7 — Web chỉ gọi gateway (10 phút)

- AppHost: `ApiBaseUrl = "http://gateway/"` (typed HttpClient + service discovery), `HubBaseUrl = gateway.GetEndpoint("http")` (URL thật).
- ⚠️ **Lỗi hay gặp:** dùng `"http://gateway"` cho SignalR → `No such host is known`: `HubConnection` **không** đi qua `IHttpClientFactory` nên không có service discovery.
- `PaymentApiClient` + trang `/admin/payments`: cùng BaseAddress (gateway), đường dẫn `payments`. DTO `PaymentSummary` do **Web tự khai báo** (không tham chiếu project của Payment).

## Bài tập

1. Tách **Menu service** (đọc thực đơn + cache Redis) khỏi Api: route `/api/products/*` của gateway trỏ sang cluster mới. Đơn hàng cần giá món → gọi HTTP sang Menu hay giữ bản sao giá qua event `ProductPriceChanged`? Viết ADR ngắn.
2. Thêm rate limiting ở gateway (`AddRateLimiter` + `RateLimiterPolicy` trên route) thay cho rate limit trong Api. Khi nào nên giữ cả hai?
3. Cho Payment service tự kiểm JWT (defense in depth) — chuyển cấu hình JwtBearer dùng chung vào 1 extension.

## Exit ticket

1. Vì sao Payment có database riêng? Nếu Payment cần tên khách thì lấy ở đâu?
2. `WithReference` và `WaitFor` khác nhau thế nào?
3. Tại sao route `/api/*` không đặt `AuthorizationPolicy` ở gateway?
4. Vì sao Web cần 2 cấu hình `ApiBaseUrl` và `HubBaseUrl`?

**Đáp án gợi ý:** (1) Đổi lược đồ/deploy độc lập, lỗi không lan; lấy từ message (thêm field vào integration event) hoặc gọi API, không đọc bảng của Order. (2) `WithReference` bơm cấu hình (connection string / địa chỉ); `WaitFor` chặn khởi động tới khi resource healthy. (3) Có endpoint ẩn danh (menu, đăng nhập) và policy chi tiết chỉ Api biết (IDOR) → Api tự kiểm. (4) HttpClient qua `IHttpClientFactory` hiểu service discovery (`http://gateway`); `HubConnection` thì không, cần URL thật.
