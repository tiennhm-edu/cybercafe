## Mục tiêu

1. Hiểu pipeline behavior = "middleware quanh handler"; so sánh với middleware HTTP (b42) và filter MVC (b43).

|--------|-----------|---------|-----------------|

## Bước 1 — `IPipelineBehavior` + dựng "củ hành" trong `Sender` (25 phút)

```csharp
public delegate Task<TResponse> RequestHandlerDelegate<TResponse>(CancellationToken ct);
public interface IPipelineBehavior<in TRequest, TResponse> where TRequest : IRequest<TResponse>
{
    Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, CancellationToken ct);
}
```

Trong `RequestWrapper.Handle`:

```csharp
RequestHandlerDelegate<TResponse> next = token => handler.Handle(typed, token);
foreach (var behavior in services.GetServices<IPipelineBehavior<TRequest, TResponse>>().Reverse())
{
    RequestHandlerDelegate<TResponse> inner = next;   // ⚠️ copy ra biến riêng
    next = token => behavior.Handle(typed, inner, token);
}
```

Đăng ký **open generic** trong `AddApplication()` — thứ tự đăng ký = ngoài → trong:

```csharp
services.AddScoped(typeof(IPipelineBehavior<,>), typeof(LoggingBehavior<,>));
services.AddScoped(typeof(IPipelineBehavior<,>), typeof(ValidationBehavior<,>));
services.AddScoped(typeof(IPipelineBehavior<,>), typeof(TransactionBehavior<,>));
```

⚠️ **Lỗi hay gặp:** `next = token => behavior.Handle(typed, next, token)` (không copy) → lambda bắt **biến** `next` đã bị gán lại → gọi chính nó → `StackOverflowException`.

Vẽ củ hành lên bảng: `Logging( Validation( Transaction( Handler ) ) )`. Hỏi: *"Đổi Validation ra sau Transaction thì sao?"* → request sai vẫn mở/đóng transaction vô ích.

## Bước 2 — `LoggingBehavior` (15 phút)

Log `→ PlaceOrderCommand`, `✓ ... xong trong X ms`, hoặc `✗ ... thất bại: DomainException` rồi **ném tiếp** (không nuốt lỗi). Chỉ log **tên kiểu** — không log nguyên request (lộ số thẻ trong `PlaceOrderCommand.CardNumber`).

Demo: chạy Api, đặt đơn → console có 2 dòng log mới bên cạnh dòng `HTTP POST /api/orders → 201` của middleware.

## Bước 3 — `ValidationBehavior` + FluentValidation (40 phút)

- Kiểm tra giấy phép trước khi thêm gói: **FluentValidation — Apache-2.0** ✓ (ghi trong `Directory.Packages.props`).
- Validator = class `AbstractValidator<T>` cạnh command:

```csharp
this.RuleFor(c => c.PhoneNumber).Must(PhoneNumber.IsValid).WithMessage("...");   // dùng lại luật của value object
this.RuleForEach(c => c.Items).ChildRules(line => line.RuleFor(l => l.Quantity).InclusiveBetween(1, 20));
this.RuleFor(c => c.CardNumber).Must(...).When(c => c.PaymentMethod == PaymentMethod.Card);
```

- Behavior chạy mọi `IValidator<TRequest>`, gom lỗi theo `PropertyName` (`"Items[0].Quantity"`) → `ValidationException` (Application) → 400 ValidationProblem cùng hình dạng `[ApiController]`.
- Có validator cho `PlaceOrderCommand`, `ChangeOrderStatusCommand`, `CancelOrderCommand`, `GetMenuQuery`.

Thảo luận: *"Api đã có DataAnnotations rồi, sao còn validate?"* → command có thể đến từ chỗ không qua `[ApiController]`. Phân vai:

| Lớp | Kiểm tra | Ví dụ |
|-----|----------|-------|
| DataAnnotations (Contracts) | Form/HTTP — báo lỗi sớm cho Web | `[Range(1, 20)]` |
| Validator (Application) | Hình dạng dữ liệu của use case | Số thẻ ≥ 12 chữ số khi chọn thẻ |
| Handler | Tham chiếu tồn tại | Mã món, mã giảm giá |
| Aggregate (Domain) | Luật nghiệp vụ theo trạng thái | Chưa trả tiền thì chưa pha |

⚠️ **Lỗi hay gặp:** `using FluentValidation;` + `ValidationException` của ta → "ambiguous reference". Dùng alias: `using ValidationException = CyberCafe.Application.Common.Exceptions.ValidationException;`.

## Bước 4 — `TransactionBehavior` + phát event sau commit (35 phút)

```csharp
if (request is not ICommandBase) return next(ct);                       // query: không cần transaction
return unitOfWork.ExecuteInTransactionAsync(token => next(token), ct);  // command
```

- Kiểm tra lúc chạy (`is ICommandBase`) thay vì ràng buộc generic → DI đăng ký open generic cho mọi request mà không lỗi.
- `IUnitOfWork.ExecuteInTransactionAsync` — cài đặt trong `CyberCafeDbContext`:
  - EF **InMemory** (test) không có transaction → chạy thẳng (`Database.IsRelational()`).
  - Đã có transaction ngoài → tham gia, không mở lồng.
  - SQL Server: `BeginTransaction` → `work` → `Commit` → **phát domain event đang chờ**; lỗi → rollback (dispose) + bỏ event.
- Nối với buổi 50: `SaveChangesAsync` thấy `CurrentTransaction != null` → **giữ** event, không phát ngay.

Demo trên SQL Server: bật log `Microsoft.EntityFrameworkCore.Database.Transaction` = `Debug` → đặt đơn thấy `Beginning transaction` → `INSERT ...` → `Committed transaction` → rồi mới có log SignalR/`LogOrderPaid`. Đổi trạng thái sai luồng → `Beginning` nhưng **không** `Committed` (rollback khi dispose), không có event.

⚠️ **Lỗi hay gặp:** gọi `Database.BeginTransaction()` trên EF InMemory → mặc định **ném** lỗi cảnh báo `TransactionIgnoredWarning`.

## Exit ticket

1. Thứ tự 3 behavior và lý do?
2. Vì sao `TransactionBehavior` kiểm tra `request is ICommandBase` lúc chạy?
3. Nếu commit lỗi, barista có nhận `OrderPlaced` không? Đoạn code nào đảm bảo?
4. Validator khác DataAnnotations ở Contracts thế nào? Có thừa không?

**Đáp án gợi ý:** (1) Logging ngoài cùng (đo/ghi mọi thứ kể cả lỗi) → Validation (dừng sớm) → Transaction (chỉ mở khi dữ liệu hợp lệ). (2) Đăng ký open generic cho mọi request; ràng buộc `where` không khớp làm DI lỗi khi resolve. (3) Không: `SaveChangesAsync` giữ event khi đang có transaction; `ExecuteInTransactionAsync` chỉ phát sau `CommitAsync`, lỗi thì xóa. (4) DataAnnotations phục vụ form/HTTP; validator bảo vệ use case dù gọi từ đâu — trùng một phần là chủ đích (defense in depth).
