## Mục tiêu

1. Phân biệt **entity** (có danh tính, so theo Id) và **value object** (không danh tính, so theo giá trị, bất biến).
2. Viết value object bằng `record`/`record struct` có validate trong constructor.
3. Lưu value object bằng **value converter** của EF Core mà không đổi cột.
4. Phát **domain event** từ aggregate và xử lý chúng **sau khi lưu thành công**.
5. Thay lời gọi `notifier` bằng tay bằng event handler — thêm phản ứng mới không phải sửa code cũ.

## Phần A — Value object (70 phút)

### Mở đầu (10 phút)

```csharp
decimal unitPrice = -5000;          // C# chấp nhận
decimal total = unitPrice + 2;      // "tiền + số ly"? C# vẫn chấp nhận
string phone = "abc";               // ai validate? Person? MomoPayment? Validator? — 3 chỗ, 3 cách viết
```

> **Giảng viên nói:** "Hai tờ 50.000 đ là **như nhau** — bạn không quan tâm tờ nào. Đó là value object: so theo giá trị. Còn 2 đơn hàng cùng 50.000 đ vẫn là **2 đơn khác nhau** — entity, so theo Id."

### Bước 1 — `Money` (20 phút)

`readonly record struct Money`: constructor ném `ArgumentException` khi âm; `+ - *` trả object **mới**; `Sum`, so sánh; `IFormattable` + `ToString(string? format)`.

- `record struct` tự sinh `Equals/GetHashCode/==` theo giá trị → `new Money(1000) == new Money(1000)`.
- Vì sao `ToString("N0")`? Razor ở Web đang viết `@item.UnitPrice.ToString("N0")` — giữ nguyên cú pháp → **Web không sửa dòng nào**.
- `OrderItem.UnitPrice`, `TotalPrice`, `Order.TotalAmount/DiscountAmount/FinalAmount` thành `Money`; `OrderMapping` lấy `.Amount` → JSON (hợp đồng với Web) vẫn là số.

⚠️ **Lỗi hay gặp:** thêm `implicit operator decimal(Money)` "cho tiện" → `money + 5` lại biên dịch được, mất ý nghĩa của value object.

### Bước 2 — Value converter (10 phút)

```csharp
builder.Property(i => i.UnitPrice)
    .HasConversion(money => money.Amount, amount => new Money(amount))
    .HasPrecision(18, 2);
```

Đọc từ DB đi qua constructor → vẫn kiểm tra không âm. `migrations add Probe` → rỗng (cột vẫn `decimal(18,2)`).
So sánh 3 cách lưu value object: **value converter** (1 cột) · `OwnsOne` (nhiều cột, owned type — như `Customer`) · `ComplexProperty` (EF 8+, nhiều cột, đúng nghĩa VO).

### Bước 3 — `OrderCode` (10 phút)

`OrderCode.From(7).Value == "CC-0007"`, `OrderCode.TryParse(" cc-0007 ", out code)`. `Order.Code` trả `OrderCode`; `Order.FormatCode(int)` (Web đang dùng) giữ lại và đi qua `OrderCode`. Không lưu cột: tính từ Id.

### Bước 4 — `PhoneNumber` (10 phút)

`PhoneNumber.Create(...)` (constructor private), `PhoneNumber.IsValid(...)` = **nguồn luật duy nhất**: `Person.IsValidPhoneNumber`, `Customer(string, PhoneNumber)`, validator của `PlaceOrderCommand` (buổi 52) đều gọi nó.

Thảo luận: *"VO có bắt buộc là kiểu riêng trong database không?"* → Không. `PhoneNumber` vẫn là chuỗi trong cột `CustomerPhone`; VO tồn tại để luật **không bị chép rải rác** trong code.

### Test — `ValueObjectTests.cs` (10 phút)

So sánh theo giá trị, không âm (kể cả phép trừ), phép toán bất biến, `ToString("N0")`, `PhoneNumber` chuẩn hóa khoảng trắng, `OrderCode` 2 chiều.

## Phần B — Domain event (70 phút)

### Mở đầu (10 phút)

Mở `b48` `OrderService`: `notifier.OrderPlacedAsync(...)` sau `SaveChanges` trong `PlaceAsync`, `notifier.OrderStatusChangedAsync(...)` trong `TransitionAsync`. Hỏi: *"Thêm 'gửi email biên nhận khi thanh toán' thì sửa mấy chỗ? Quên 1 chỗ thì sao?"*

### Bước 5 — Event là record thì quá khứ, aggregate `Raise` (15 phút)

```csharp
public sealed record OrderPaid(Order Order, Money Amount, DateTime OccurredAt) : IDomainEvent;
public sealed record OrderPlaced(Order Order, DateTime OccurredAt) : IDomainEvent;
public sealed record OrderStatusChanged(Order Order, OrderStatus From, OrderStatus To, DateTime OccurredAt) : IDomainEvent;
```

- `Pay()` → `Raise(OrderPaid)` + `Raise(OrderPlaced)` (luật quán: trả tiền xong mới vào hàng chờ của quầy).
- `TransitionTo(...)` → `Raise(OrderStatusChanged(from, to))`.
- Aggregate chỉ **ghi lại** — không biết SignalR, không biết ai nghe.

Câu hỏi: *"Sao event giữ cả `Order` chứ không chỉ `OrderId`?"* → Id là IDENTITY, lúc `Raise` còn = 0; event được phát **sau** `SaveChanges` nên đọc `order.Id` lúc đó là đúng. Đổi lại: handler chỉ được **đọc**.

### Bước 6 — Phát SAU khi lưu: override `SaveChangesAsync` (20 phút)

`CyberCafeDbContext`:

```csharp
public override async Task<int> SaveChangesAsync(bool acceptAllChangesOnSuccess, CancellationToken ct = default)
{
    int rows = await base.SaveChangesAsync(acceptAllChangesOnSuccess, ct); // lỗi → event không bao giờ được phát
    this._pendingEvents.AddRange(this.TakeDomainEvents());                 // lấy + Clear trên aggregate
    if (this.Database.CurrentTransaction is null) await this.PublishPendingEventsAsync(ct);
    return rows;
}
```

- `IDomainEventPublisher` (Application) inject qua constructor DbContext, **tùy chọn** (`= null`) để `dotnet ef` và test tự `new` DbContext vẫn chạy.
- Đang trong transaction tường minh → giữ lại, phát sau commit (buổi 52 hoàn thiện).

Vẽ timeline trên bảng: `Pay()` (Raise) → `SaveChanges` (INSERT) → lấy event → phát → SignalR. So với cách sai: phát trong `Pay()` → lưu lỗi → barista đã thấy đơn "ma".

⚠️ **Lỗi hay gặp:** không `ClearDomainEvents()` sau khi lấy → lần `SaveChanges` sau (cùng DbContext) phát lại event cũ → barista nhận 2 lần.
⚠️ **Lỗi hay gặp:** dùng `SavingChanges` (TRƯỚC khi lưu) để phát → lưu lỗi vẫn đã báo.

### Bước 7 — Publisher + handler (25 phút)

- `DomainEventPublisher`: theo **kiểu thật** của event, lấy mọi `IDomainEventHandler<TEvent>` từ DI (kỹ thuật wrapper generic + cache — giống `Sender` buổi 51). Handler lỗi → **log, không ném** (dữ liệu đã lưu; ném ra thì khách thấy 500, bấm đặt lại → đơn trùng).
- `Orders/EventHandlers/OrderEventHandlers.cs`:
  - `NotifyBaristasOnOrderPlaced` → `notifier.OrderPlacedAsync(order.ToDto())`
  - `NotifyOnOrderStatusChanged` → `notifier.OrderStatusChangedAsync(...)`
  - `LogOrderPaid` → log số tiền + phương thức (không log số thẻ)
- `AddApplication()` quét đăng ký mọi `IDomainEventHandler<>`.

Demo: 2 tab (barista + khách) như b47 — mọi thứ vẫn realtime, nhưng **không còn dòng nào gọi `notifier` trong use case**. Test tích hợp `DomainEvents_ArePublishedOncePerChange_AfterSave`.

> Thêm phản ứng mới = thêm 1 class. Sửa đổi = 0 dòng ở `Order` và command handler (Open/Closed principle).

## Exit ticket

1. 3 tính chất của value object?
2. Value converter khác owned type ở chỗ nào?
3. Vì sao domain event phải phát **sau** `SaveChanges`, không phải trong `Pay()`?
4. Handler domain event ném exception thì request có lỗi không? Vì sao thiết kế như vậy?

**Đáp án gợi ý:** (1) So sánh theo giá trị, bất biến, tự validate. (2) Converter: 1 VO ↔ 1 cột; owned type: VO nhiều cột, EF quản lý như entity phụ thuộc. (3) Lưu lỗi thì sự kiện "chưa xảy ra" — phát sớm là báo sai. (4) Không — chỉ log: dữ liệu đã lưu thành công, side effect là best-effort; cần chắc chắn thì Outbox (b55).
