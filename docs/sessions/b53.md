## Mục tiêu

1. Giải thích vì sao phía **đọc** không cần aggregate (không sửa → không cần invariant, không cần tracking).
2. Viết read model bằng **projection** (`Expression` → SELECT đúng cột) + `AsNoTracking`; đặt luật IDOR ngay trong `WHERE`.
3. Đưa đọc thực đơn (có cache) vào query; hub dùng chung query với REST.
4. Kiểm luật DDD/CQRS bằng architecture test.
5. Tổng kết chặng 48–53, chuẩn bị cho microservice (b55).

## Mở đầu — cái giá của đọc bằng aggregate (15 phút)

So sánh câu SQL của `GET /api/orders` ở `b48` (Include đủ: mọi cột `Products` gồm `Description`, `Price`, `BeanType`, `TeaType`, `Flavor`...; EF tracking từng object) với `b53`.

## Bước 1 — `IOrderReadStore` + projection (40 phút)

Port ở Application (`Orders/Queries/IOrderReadStore.cs`) trả **DTO**; cài đặt ở `Infrastructure/Persistence/ReadModels/OrderReadStore.cs`:

```csharp
private static readonly Expression<Func<Order, OrderRow>> Projection = o => new OrderRow(
    o.Id, o.Status, o.CreatedAt, o.Customer.FullName, o.Customer.PhoneNumber, o.Customer.LoyaltyPoints, o.Note,
    o.Items.OrderBy(i => EF.Property<int>(i, "Id"))
           .Select(i => new OrderLineRow(i.Product.Id, i.Product.Name, i.Product.Emoji, i.Product is Drink, i.Size, i.Quantity, i.UnitPrice))
           .ToList(),
    o.Discount, o.Payment);
```

- `i.Product is Drink` thay cho `HasSize` (code C#, EF không dịch được) → điều kiện trên cột discriminator.
- `Discount`/`Payment` vẫn chiếu thành object domain nhỏ vì `Display()` đa hình (bài OOP) — không có cách viết SQL tương đương gọn.
- Tổng tiền tính lại trong bộ nhớ **cùng công thức** với aggregate.

**IDOR trong `WHERE`:**

```csharp
.Where(o => o.Id == id && (isStaff || (o.OwnerId != null && o.OwnerId == userId)))
```

⚠️ **Lỗi hay gặp:** bỏ `o.OwnerId != null` → EF bù "null semantics" kiểu C# (`NULL == NULL` là true) → người dùng `userId = null` thấy được đơn cũ không chủ.
⚠️ **Lỗi hay gặp:** read model tự "sáng tạo" công thức khác phía ghi → màn hình quầy lệch số tiền đã thu. Test canh: `ReadModel_MatchesWriteModel` so JSON của `POST` (ghi), `GET /{id}`, `/mine`, bảng quầy.

## Bài tập (cả chặng)

1. **Read model riêng bằng event:** tạo bảng `BaristaBoard` (Id, Code, Status, tóm tắt món, FinalAmount) cập nhật bởi handler `OrderPlaced`/`OrderStatusChanged`; `GetBaristaBoardQuery` đọc bảng này. Cần migration mới. So sánh độ phức tạp với projection hiện tại.
2. **Dapper (tùy chọn):** viết `DapperOrderReadStore : IOrderReadStore` cho SQL Server (`SELECT ... FROM Orders o JOIN OrderItems ...`). Kiểm tra giấy phép Dapper (Apache-2.0). Đổi đăng ký DI — Application có phải sửa không?
3. Viết `GetDailyRevenueQuery` thay cho `IRevenueReportService` + validator khoảng ngày (thay kiểm tra trong `ReportsController`).

## Exit ticket

1. Vì sao query handler không dùng `IOrderRepository`?
2. `AsNoTracking` + projection tiết kiệm được gì? Đánh đổi gì?
3. Luật IDOR của `GET /api/orders/{id}` nằm ở đâu? Hub dùng lại thế nào?
4. Kể 3 quyết định trong chặng 48–53 giúp tách microservice ở b55 dễ hơn.

**Đáp án gợi ý:** (1) Đọc không sửa → không cần aggregate, invariant hay tracking; repository là cửa GHI. (2) Ít cột, ít object, không theo dõi thay đổi → nhanh, ít RAM; đổi lại phải giữ công thức tính khớp phía ghi. (3) Trong `WHERE` của `OrderReadStore.GetByIdAsync`; hub gửi cùng `GetOrderByIdQuery`. (4) Port + adapter (đổi hạ tầng không sửa nghiệp vụ); aggregate tham chiếu nhau bằng Id (`OwnerId`); domain event (sẽ thành message qua broker + Outbox).
